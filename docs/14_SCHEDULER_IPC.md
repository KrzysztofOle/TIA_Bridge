# 14 — Scheduler, Supervisor i IPC B-02B

Stan 2026-10-25: zaimplementowany scheduler biblioteczny, nadzór własnego procesu Fake Worker i wersjonowany IPC. Zakres B-02B jest wykonaniem syntetycznym offline. Bieżące [B-02C](15_HTTP_API_CLI.md) dodaje HTTP/CLI; nadal brak Siemens lub rekoncyliacji rzeczywistego projektu. Obowiązują [architektura 03](03_ARCHITECTURE.md), [synchronizacja 04](04_SYNCHRONIZATION.md), [interfejs 05](05_CODEX_INTERFACE.md), [backlog](08_IMPLEMENTATION_PLAN.md) i [Storage B-02A](13_DURABLE_STORAGE.md). B-02D i X-01 nadal wymagają odrębnych zadań.

## Scheduler i ownership

[OperationScheduler](../src/TiaBridge.Host/Scheduling/OperationScheduler.cs) korzysta wyłącznie z istniejącego SqliteOperationStore/outbox. `Start()` uruchamia pętlę w tle; submit i odczyt statusu nie czekają na nią. `PumpOnceAsync` jest tym samym krokiem, udostępnionym do kontrolowanych testów. Nie wolno uruchamiać dwóch pętli na jednej instancji. Status czyta SQLite bez wchodzenia do schedulera lub IPC. Test wykonuje 1000 odczytów metadata statusu przy rzeczywistym wiszącym procesie i sprawdza p95 ≤100 ms; nie jest to pomiar HTTP, 8 klientów ani całej bramki B-02C/D.

Jeden zatwierdzony state root ma wyłączny plik `scheduler.lock` (FileShare.None). Ownership DB zawiera host PID/start, SID Windows, host epoch, rosnący fence i lease. Worker ma osobne PID/start/epoch i weryfikowaną tożsamość. Portal/capability to jawny klucz z zaufanego profilu, projekt to istniejący ProjectKey z Core. Pierwszy profil serializuje globalnie do jednego aktywnego call na state root, także dla różnych projektów/portali. Nie wolno uruchamiać niezależnych produkcyjnych state root jako obejścia właściciela tego samego portalu.

Scheduler najpierw weryfikuje jawny profil syntetyczny. Brak profilu daje UNSUPPORTED bez uruchomienia procesu. Profil nie jest capability/grantem Siemens; nie bierze się go z niezaufanego request JSON. Przygotowuje immutable artifact wejścia. W jednej transakcji zapisuje QUEUED, przejęcie istniejącego outbox, DISPATCH_RECORDED, RUNNING, journal oraz attempt/step intent z epoch, fence, input hash, expected plan hash i deadline. Dopiero po commit wysyła IPC. Anulowanie używa tej samej ścieżki transakcyjnej: przed dispatch daje CANCELLED bez wysłania, po rozpoczęciu zapisuje tylko cancel intent. Worker potwierdza granicę bez efektu albo host zachowuje RUNNING/UNKNOWN. Cancel podczas potwierdzonego no-effect backoff kończy bez następnej próby.

`IWorkerSupervisor` / `IWorkerConnection` oddzielają scheduler od uruchamiania procesu. Jedyna dostarczona implementacja to FakeWorkerSupervisor. Zastąpienie jej adapterem V19 nie wymaga drugiego schedulera/ledgeru, lecz nadal wymaga X-01, kwalifikacji protokołu, uprawnień i zasobów vendor. DTO IPC nie są binarną biblioteką Core dla net48.

## Supervisor i proces

[Supervisor](../src/TiaBridge.Host/Supervision/WorkerSupervisor.cs) uruchamia wyłącznie jawnie wskazany zbudowany TiaBridge.FakeWorker.dll przez dotnet, bez shell i widocznego okna. Nie enumeruje ani nie uruchamia TIA. Handshake sprawdza PID peer pipe przez Win32, czas startu procesu, nonce, worker ID i build. Bootstrap secret jest losowy per połączenie i trafia przez odziedziczone stdin, bez argv/logów/Git. Oczekiwanie na handshake ma 10 s; zapis IPC ma limit 1 s i nie trzyma transakcji DB. Własny proces, który nie ukończył handshake i nie dostał dispatch, może zostać zakończony podczas sprzątania błędnego startu.

Dispose wysyła stop syntetycznego workera, zamyka pipe i czeka najwyżej 5 s na własne dziecko. Nie ma wymuszonego zabijania działającego wykonawcy, Thread.Abort, KILL_ON_JOB_CLOSE ani sterowania obcymi procesami. Fake kończy własne opóźnienie po utracie IPC. Tego zachowania nie przenosi się na Siemens; polityka parent-loss/Job Object/Dispose rzeczywistego workera pozostaje X-01. Przerwane RUNNING nie jest oznaczane jako sukces przy Dispose.

## Wersjonowany IPC

[Kontrakt IPC 1.0](../contracts/ipc/v1/message.schema.json), [przykłady dziewięciu rodzajów komunikatów](../examples/ipc/v1/hello.json), [implementacja ramki](../src/TiaBridge.Ipc/Protocol.cs). Kontrolne Hello/Ready/Heartbeat/Stop mają operation_id=null, fence=0; Dispatch/Started/Progress/Receipt/Cancel mają UUID operacji i dodatni fence. Każdy komunikat ma protocol_version, worker_epoch i monotoniczną sequence w danym kierunku. Protocol 1.0 odrzuca inne wersje, missing/unknown/duplicate pola, błędne typy/enumy/UUID, nieprawidłowe hash/ref i replay sequence. Dziewięć wspólnych przykładów jest sprawdzanych w .NET i niezależnym JSON Schema Python.

Ramka: 4-bajtowa długość little endian, dokładne UTF-8 JSON i 32 bajty HMAC-SHA256 nad tym JSON. Długość obejmuje JSON+MAC i nie przekracza 1 MiB; host sprawdza ją przed alokacją. MAC porównuje constant-time. To integralność i uwierzytelnienie sesji, bez deklaracji szyfrowania. JSON ma maksymalną głębokość 32. Pojedynczy receipt/report inline ma maksymalnie 64 KiB UTF-8; większy wynik musi być referencją do zarządzanego artefaktu w typowanym result. Nie przesyła się proxy ani typów Siemens.

Pipe ma losową nazwę i CurrentUserOnly po obu stronach, FirstPipeInstance po stronie serwera. Windows sprawdza bieżącego użytkownika i poziom elevation, a kod dodatkowo sprawdza PID peer. Zasady BCL: [CurrentUserOnly](https://learn.microsoft.com/en-us/dotnet/api/system.io.pipes.pipeoptions?view=net-10.0), [peer PID](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeclientprocessid). Nie kwalifikuje to ochrony przed administratorem lub wrogim procesem tego samego użytkownika. Próby z obcego SID nie są wykonywane w obecnej sesji testowej; wdrożeniowa kwalifikacja ACL wymaga odrębnego środowiska.

Dispatch zawiera wyłącznie artifact IDs/SHA dla requestu i syntetycznego wzorca wyniku, scenario/delay i dane korelacji. Worker sprawdza generated ID, containment, przodków/reparse points, rozmiar i SHA przed odczytem. Wzorzec wyniku jest jawnie danymi Fake, nie dowodem TIA. Host waliduje otrzymany raport przez istniejący ContractJson i sprawdza epoch/fence/attempt/input hash/expected plan hash. Niezgodny receipt jest zachowywany jako FENCED_REJECTED, bez promowania stanu. Błąd protokołu lub nieprawidłowy wynik nie potwierdza wykonania.

## Heartbeat, watchdog i retry

Worker wysyła heartbeat co 2 s z zadania niezależnego od wykonania. Host aktualizuje swój heartbeat i odnawia lease 15 s; brak heartbeat workera od 6 s oznacza podejrzenie utraty. Deadline wyznacza istniejący ExecutionBudget z requestu, oddzielnie od queue timeout (domyślnie 300 s). `last_progress_at` aktualizują Started/Progress, heartbeat nie jest postępem. `tia_probe_at=null` w Fake; żaden health nie wykonuje probe inline. Observation pokazuje wiek postępu, PID/epoch oraz IDLE/BUSY/SUSPECT/QUARANTINED. Odczyt statusu nie czeka na send/read workera.

Timeout read kończy operację FAILED, ale utrzymuje aktywny slot, aż nadejdzie quiescent receipt lub zostanie potwierdzony koniec dokładnego procesu. Nowa próba nie nakłada się na stary call. Timeout/loss mutacji po trwałym dispatch daje RECONCILIATION_REQUIRED/UNKNOWN, quarantine i blokadę właściciela. Lease expiry nie zwalnia tej blokady.

[RetryPolicy](../src/TiaBridge.Host/Scheduling/ExecutionModels.cs) dopuszcza maksymalnie 3 próby łącznie tylko dla jawnie zakwalifikowanego, bezefektowego odczytu, po receipt Rejected/0 effects/quiescent. Backoff 1/2 s + jitter do 25%, w ramach wspólnego deadline. Identity/schema/auth/conflict oraz potencjalna mutacja nie mają retry. Timeout nie jest automatycznie ponawiany. Próby pozostają w tym samym operation_id i nowych attempt/step intent, bez cofania terminalnego lifecycle lub outbox do PENDING.

[Circuit breaker](../src/TiaBridge.Host/Scheduling/CircuitBreaker.cs) jest utrwalany per portal/capability: 3 awarie w 60 s, cooldown 60 s i jeden kwalifikowany read w half-open. Pomyślny receipt zamyka breaker, kolejna awaria odnawia cooldown. Quarantine ma pierwszeństwo. Testy używają kontrolowanego zegara i jawnego źródła jitter; mechanizm nie zależy od losowego kill procesów.

## Quarantine i restart

Migracja `003_execution.sql` rozszerza dotychczasową quarantine o worker_epoch/fence i dodaje scheduler_ownership, worker_processes, dispatch_attempts, worker_receipts i circuit_breakers. Stare migracje/hash pozostają niezmienione. Istniejący steps przechowuje attempt intent, leases wiążą metadane właściciela z projektem. Receipt journal jest append-only z SHA, a terminalne state/result/event nadal korzystają z jednej transakcji B-02A. Receipt jest utrwalany przed użyciem wyniku; późniejszy błąd zapisu wyniku nie daje SUCCEEDED.

Po restarcie nowy owner/fence odtwarza kolejkę z tego samego magazynu. RUNNING możliwej mutacji od razu przechodzi do trwałego UNKNOWN/quarantine. Nie adoptuje się starego workera: PID/start są tylko obserwowane. Żywy lub niedostępny do sprawdzenia proces blokuje nowe wywołania. Historyczny odczyt może zostać zamknięty FAILED; nowa niezależna operacja read może ruszyć dopiero po potwierdzeniu końca dawnego procesu. Nie cofa się starego wyniku ani nie wykonuje starego intentu ponownie. Globalny barrier może zwolnić wyłącznie po stwierdzeniu braku starych procesów i braku UNKNOWN/quarantine; kwarantanna mutacji nie ma automatycznego clear API.

Spóźniony sukces po timeout zostaje w worker_receipts jako LATE_OR_DUPLICATE. Nie zmienia terminalnego UNKNOWN na SUCCEEDED i nie usuwa quarantine. Host nie implementuje fikcyjnego readback/reconciliation TIA; odblokowanie wymaga przyszłego jawnego workflow, świeżej tożsamości, quiescence i planu. Dispatch dedupe Fake jest ograniczone do sesji/epoch oraz maksymalnie 1000 kluczy; po crash ochronę zapewnia trwały host i brak replay mutacji, nie ulotny cache workera. Nie jest to exactly-once Siemens.

## Fake i dowody

[Fake Worker](../src/TiaBridge.FakeWorker/Program.cs) realizuje Success, DelayedSuccess, FailBefore, FailAfter, Hang, NoHeartbeat, HeartbeatWithoutProgress, Timeout, Disconnect, Exit, LateSuccess, UnknownMutation, Cancellable, DuplicateDispatch, SuccessAfterRetry oraz negatywne WrongFence/WrongPlanHash. Scenariusz i opóźnienie pochodzą z jawnego profilu testowego. Wykonanie jest serializowane; powtórzony identyczny dispatch ma cached receipt albo czeka na tę samą próbę, bez ponownego zwiększenia syntetycznego effect counter. Niezgodny duplikat blokuje połączenie. Nie ma reflection/wykonywania kodu z artefaktu.

LateSuccess czeka na jawny ponowny identyczny dispatch, który zwalnia już rozpoczętą próbę bez nowego efektu. Test przechwytuje transport, przesuwa kontrolowany zegar za deadline, zwalnia odpowiedź i czeka na rzeczywistą ramkę przed kolejnym krokiem hosta. Udowadnia to również, że receipt już czekający w kolejce nie wyprzedzi kontroli deadline po deschedulingu hosta. Pozostałe opóźnienia mają zadany czas; testy czekają na obserwowane stany z ograniczonym deadline, bez losowego kill.
